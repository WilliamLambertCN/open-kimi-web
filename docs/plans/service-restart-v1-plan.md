# 会话设置一键重启服务 · v1

## 目标

设计要求在 Open Kimi Web 的会话设置中添加一键重启，并在当前连接断开后恢复访问。
同时授权重启当前通过 `kimi web --host` 启动的服务。保留已有 TTFT／TPS 与侧聊选模代码，不提交或发布。

## 当前补充 · 2026-11-12

用户已要求提交发布，并指定桌面入口移到“设置 → 通用／General”，手机仍在会话设置，不保留桌面重复入口。
按[2.5.2-r3 发布计划](request-metrics-2.5.2-r3-release-v1-plan.md)执行，覆盖下方“不提交／不发布”的历史阶段限制。
保留首次启用失败记录；本轮发布不重启生产，也不将现场停止故障写成已修复。

## 方案

- 在官方设置中追加“重启服务／Restart service”操作：桌面在“通用”，手机在会话设置，使用相同功能、主题和语言。
  这是一次性操作按钮，不是会让人误以为长期启用的开关。确认时说明影响连接同一服务的所有设备。
- 仅受管 `kimi web` 启动方式提供重启；独立 `serve --target` 不控制外部后端。
- 服务端增加固定白名单 GET 状态及 POST 重启接口，沿用有效 Bearer 授权；拒绝跨站、编码别名、额外参数和大正文。
  不启用 debug、不允许浏览器指定命令、目录、环境、端口或 PID。
- 接受请求前阻挡新的代理写请求，并检查正式会话列表中运行／等待审批／等待回答状态；有工作则拒绝，不强制取消。
  同时检查在途写请求。不能验证空闲或后端身份则拒绝，不靠读写真实日志判断。
- 原 launcher 准备独立 worker，收到确认后才优雅停止自己的后端与前端；worker 不在后端工具进程树内。
  worker 等旧 launcher 退出，再按原 Node、参数、工作目录、环境启动，不打开新网页、不更新软件。
  保留 token、数据目录、HTTPS 根信任与外部监听端口。新服务通过私有 IPC 回执确认就绪；失败只做有界重试。
- 浏览器在原地址查询新实例标记，确认启动成功；原生 WebSocket 恢复原会话。
  不自动重发用户消息、不恢复未完成生成、不强制刷新以免丢失未发送草稿；提供刷新按钮加载新界面。
  失败提供原命令的人工恢复说明，不把接受重启误报为已恢复。
- 本次首次启用使用 ignored cache 中独立于当前后端的临时任务，等当前回复结束且服务连续空闲后执行。
  不在当前模型调用尚未结束时终止本服务，不改真实会话或网络。

## 变更与验证

1. 独立 restart 模块负责授权、状态、忙时门禁及 worker 协议；supervisor 只连接生命周期，不复制会话引擎。
2. 独立手机资源负责原生设置入口、确认、重连进度与双语，不访问 Vue 私有状态。
3. UT 覆盖鉴权、跨站、路径、正文、重复请求、忙时拒绝、worker 启动失败／取消／重试和同配置重启。
4. IT 通过实际 launcher 验证接口、写门禁、资源注入、自定义前端隔离与 owned process 清理。
5. 准确官方 2.5.2、隔离 home／工作区实际重启两次，核对同端口／授权／数据及原生 WS 恢复，不使用付费模型。
6. 完整官方 app 以原版为基线检查双端、长短文案与三主题实图、焦点、取消、失败和重复点击。
7. 本轮是跨层生命周期变更，运行标准 lint、typecheck、UT、IT 和 pack，覆盖率门槛与默认并发不变。
8. 启用前只做相关增量隐私检查；验后清理自有进程、端口和运行数据，证据归档 ignored cache。

## 假设与边界

- 重启会断开所有设备，不是只重启当前会话；入口虽在会话设置，文案必须说明服务级影响。
- 仅重启当前 OKW 管理的进程，不管理另一独立 CLI；不保证恢复已经中断的模型生成或浏览器没发送的消息。
- 不以原版没有的原子锁承诺阻挡直接访问回环后端的其它程序；检查期间网页代理写入必须阻挡。
- 自动重连不等于自动全页刷新；新界面通过明确刷新操作加载，原草稿保持在当前页面。
- 实体手机与非 Windows 宿主若未实测必须明示；启动代码本身损坏时有界重试不能替代终端恢复。

### 事件：Windows新服务收到就绪回执后立即消失

- 影响：隔离测试中重启确认后网页持续等待，新后端残留而新前端不可用；未部署到用户服务。
- 触发条件：Windows新launcher没有detached，临时worker收到ready即退出。
- 根因：新launcher仍附着临时进程的控制台生命周期，worker退出时被带掉；原mock不包含操作系统进程生命周期。
- 证据：有限trace记录ready后worker退出，新前端不在但backend仍监听；最小对照只有detached=true持续响应。
- 修复：新launcher跨平台独立启动，保留私有IPC就绪确认；启动失败且父进程已退出时不声称子树已清，不继续重试。
- 回归验证：新增真实worker退出后HTTP仍响应的IT、退出后清理未确认UT，完整2.5.2重启两次通过。
- 运维动作：首次启用须重启旧launcher；产品不强刷用户页面。
- 剩余边界：实体手机及非Windows宿主未实测；未知官方版本、随机端口和外部target不开放重启能力。

### 事件：后端登记了旧端口，launcher过早验证而失败

- 影响：同机存在固定后端端口占用时，新受管服务可能在startup中失败；真实隔离验证先复现HTTP401。
- 触发条件：官方2.5.2先登记请求端口，监听冲突后改用下一个端口并更新同一登记。
- 根因：旧launcher只读取一次登记，初始端口指向另一实例；它的token不同，正确地拒绝了鉴权。
- 证据：准确官方start源码顺序及真实第一次startup日志；同一登记随后变端口，PID与身份未变。
- 修复：在原三秒总验证窗口内重读同server_id／PID／started_at，仅端口确实变化才重新验证健康和鉴权。
- 回归验证：六项登记变化边界UT、完整supervisor IT及真实2.5.2启动／重启通过。
- 运维动作：随launcher重启生效，不改端口配置、不放宽token或直接跳过401。
- 剩余边界：登记丢失、身份变化、端口非法或验证仍失败均拒绝启动。

### 事件：完整并发IT的旧Windows taskkill探测超时

- 影响：标准IT一次失败，未放行生产启用；旧测试原有按能力skip不能掩盖超时。
- 触发条件：Windows标准默认并发，运行忽略优雅关闭的cmd shim测试。
- 根因：taskkill探测超过runCapture五秒期限；supervisor兜底同样依赖它，退出确认存在实际风险。
- 证据：`restart-standard-it.log`保留1失败／653通过，错误来自canTaskkillTree，不归咎于PID残影。
- 修复：supervisor记录spawn创建时间，复用项目现有原生句柄子树清理；fixture同用它并直接断言，不再能力skip。
- 回归验证：20项supervisor IT及默认并发完整IT654项通过，原生清理三秒期限不变。
- 运维动作：随launcher更新，不按node进程名杀进程；无法确认退出仍报告错误。
- 剩余边界：Windows系统限制原生调用时仍会失败，不冒充已清理。

## 首次启用的运维边界

- 从旧服务首次切换到受管重启，与已经启用后的隔离连续重启是不同场景。
- 曾有停止阶段失败而未进入新实例启动的记录；缺少具体异常，不能认定为管理员权限派生问题。
- 既有隔离通过不证明首次迁移故障已修复；保留人工恢复方式，不自动重跑旧进程身份脚本。
- 私人操作时间和实际进程状态不进入公开记录；生产重试需明确授权和分阶段诊断。
